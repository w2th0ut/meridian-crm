# 获客 → 触达验收清单

用现有账号在本地走一遍。不要编造联系人，也不要为了走通而跳过确认框。话机页面不在这条路径里。

## 0. 准备

```bash
npm install
npm --prefix whatsapp-plugin install --workspaces=false
npm run dev
```

- CRM：`http://127.0.0.1:5188/`
- 用有 `prospect.read` / `prospect.execute` 和 `communication.send` 的业务员或管理员登录。
- 发开发信前，个人设置里要有发件邮箱；没有就停在草稿，不要改发送接口。
- 客户沟通依赖本机 WhatsApp 插件。插件没起来时，页面应停在连接状态，而不是假装已发送。

## 1. 搜索预览

1. 侧栏第一组里，工作台后面应是「智能获客」，再是搜客清单、线索、客户沟通、开发信。
2. 「话机（可选）」在下方折叠分组里，不在主导航第一组。
3. 打开智能获客，用自然语言或结构化表单写一个真实搜索目标，点「新建搜客任务」。
4. 确认任务进入队列，并能看到进度（来源、清洗或候选），而不是点完就当完成。

## 2. 可联系候选

1. 打开搜客清单。
2. 筛「可联系」。没有可联系候选时，先在待处理里查公开联系方式，不要手写假邮箱或假号码。
3. 点开一条可联系候选。详情里应能看到「写开发信草稿」和「转为线索」。
4. 「写开发信草稿」展开清单上的草稿区，并按这家公司已有的公司名、联系人、业务线索预填主题和正文。缺邮箱或联系人时，草稿区写明缺什么，不编造。不会发送。要外发仍要点「发送开发信」，并在确认框里确认。

## 3. 转为线索

1. 在搜客清单或候选详情上看「转为线索」资格。未达门禁时写明缺什么，不出现转入按钮，也不能改走同步接口绕过。
2. 已有当前业务员的人工可联系批准、且还不是线索时，点「转为线索」。先出确认框。取消后不调用转换接口。
3. 确认后走现有 `POST /api/prospects/:id/convert-to-lead`。成功后可以「查看线索」，或留在清单写开发信、去客户沟通。这一步不发送开发信。
4. 已经是线索的不再转入。失败时页面展示服务端或业务错误，不静默吞掉。
5. 没有可解析的 WhatsApp 号码时，不出现「打开 WhatsApp」。有号码时，该按钮只在网页版打开会话，CRM 不自动发消息。
6. Agent 工具 `prospect.convert_to_lead` 的规则不变：没有当前业务员的 `approved_contactable` 批准记录就不能转。没有新增权限，也没有放宽这道门禁。

## 4. 起草触达

1. 从已入线索的候选点「写开发信」，或从线索抽屉点「写开发信」。
2. 开发信页应带上这家公司的草稿。发送按钮在确认前不得把信发出。
3. 点「去客户沟通」只进入客户沟通页。未连接时停留在连接提示。
4. 直接打开侧栏「开发信」且还没选对象时，应看到去获客 / 搜客清单 / 线索的入口，而不是空白页或自动生成。

## 5. 搜客进度可见

1. 打开工作台。有未结束的搜客任务时，「进行中的搜客」只列出这些任务的标题、状态、来源结束数和候选数。点一行进入该任务的执行详情。
2. 没有进行中的任务时，这里只提示去智能获客，不出现编造的数字。
3. 打开智能获客。标题下方的「搜客进度」显示状态、来源收获、清洗去除和候选入池。接口还没回传的数字写「尚未回传」。
4. 任务还在排队、执行或暂停时，状态是等待中、执行中或已暂停，进度不到 100%，并写明「尚未结束」。结束后才显示「已结束」。
5. 点「刷新进度」。数字和阶段与任务详情一致，刷新失败时停在错误提示，不把未结束任务改成已结束。

## 6. 开发信草稿预填

1. 在搜客清单打开一条可联系候选，点「写开发信草稿」。主题里应有公司名；正文里应有公司名，以及资料里已有的联系人或业务/产品线索。收件邮箱只来自候选上已有的地址。
2. 联系人是「待维护」或为空、没有邮箱、没有业务方向时，草稿区的「草稿待补齐」写明缺哪一项。主题和正文里不要出现编出来的邮箱，也不要把空业务写成某一种采购场景。
3. 智能获客里，已加入搜客清单且状态为可联系或已联系的候选，详情里有「写开发信」。点进去应落到同一份预填草稿，不会自动发送。
4. 线索里打开 Example Lighting GmbH，点「写开发信」。开发信页的主题含公司名，正文含 Alex Buyer，并带上备注里的 LED 照明线索。发送按钮仍要再点「确认发送」才会发出。
5. 改完草稿后若要外发，只通过「发送开发信」并确认。取消确认框后，草稿还在，信没有发出。

## 7. 待写开发信

1. 打开工作台。「进行中的搜客」下面有一块「待写开发信」。
2. 没有符合条件的候选时，这里写明：去智能获客或搜客清单，补齐可联系状态和邮箱。不要出现编出来的公司名。
3. 只列出已经在搜客清单里、状态是可联系、联系方式里已有邮箱、并且还没有发过开发信的候选。每一行是公司名、可联系、有邮箱。最多 8 行。待处理、已联系、已排除、没有邮箱、已经发过开发信的都不出现。
4. 打开搜客清单。同一条候选上有「可写开发信」。没有邮箱或已经发过的不标。
5. 点工作台的一行。应进入搜客清单，并打开和「写开发信草稿」相同的草稿区。主题和正文按这家公司已有资料预填，收件邮箱只来自候选上已有的地址。页面不会自己发送。
6. 要外发仍要点「发送开发信」，并在确认框里确认。取消确认框后草稿还在。发出之后，这条从「待写开发信」消失。
7. 点「刷新」。名单跟当前搜客清单一致。刷新失败时停在错误提示，不改成一份假名单。

## 8. 已发开发信可见

1. 打开工作台。「待写开发信」下面有一块「最近触达」。
2. 没有已发开发信时，这里写明：去待写开发信或搜客清单写一封，确认发送后才会出现。不要出现编出来的公司名。
3. 只列出已经在搜客清单里、并且有开发信发送时间的候选。每一行是公司名、已发开发信、发送时间。最多 5 行，按发送时间从新到旧。还没发出的不出现。
4. 点一行。应进入搜客清单并选中该候选，清单行上能看到「已发开发信」。草稿区保持收起。页面不会再次发送。
5. 在搜客清单对一条待写候选点「发送开发信」，先取消确认框。这条仍留在「待写开发信」，清单上不标「已发开发信」，「最近触达」也不出现它。
6. 再点「发送开发信」并确认。成功后这条从「待写开发信」消失，清单行标「已发开发信」，并出现在「最近触达」。取消或发送失败时，不要把它算成已发。
7. 点「刷新」。名单跟当前已发记录一致。刷新失败时停在错误提示，不改成一份假名单。

## 9. 话机保持次要

1. 工作台文案把获客和触达放在前面，不把坐席外呼当主行动作。
2. 从「话机（可选）」仍能打开话机工作台、通话记录、回访策略、话机配置。
3. 四个话机页面标题不变，副文案标明这是可选遗留能力。

## 9. 缺项补齐后回到同一份草稿

1. 打开搜客清单，选一条可联系、但没有邮箱，或联系人是「待维护」的候选。点「写开发信草稿」。
2. 「草稿待补齐」写明缺什么。缺邮箱时旁边有「去补邮箱」，缺有效联系人时有「去补联系人」，缺公司名时有「去补公司名」。主题和正文里仍然没有编出来的邮箱，空着的联系人不会被写成收件人。
3. 点「去补邮箱」。草稿区展开的是这条候选的资料，不是另一家公司，也不是开发信收件框里的临时字。邮箱框是空的。说明里写着不会编造、不会发送。
4. 什么都不填就点「保存并重新预填」，应停住，并说明空着的项不会写成假数据。候选资料不变，收件人仍空。
5. 填一个不完整的邮箱再保存。应停住，并说明要已核实的真实地址。不会发出保存请求，草稿收件人仍空。
6. 只填上已核实的邮箱再保存。页面仍停在搜客清单、同一条候选、同一份开发信草稿。收件人变成这个邮箱；联系人如果还是占位，称呼里仍然不要出现「待维护」。公司名还在主题里。「去补邮箱」消失；联系人仍缺时「去补联系人」还在。
7. 点「去补联系人」，把「待维护」改成真实姓名，再保存。称呼里出现这个姓名，收件人仍是上一步的邮箱。信没有发出。
8. 要外发仍要点「发送开发信」，并在确认框里确认。取消确认框后草稿还在。

## 10. 本地演示：转为线索资格

用一条真实候选看资格，不要为了走通去改 `convert_to_lead` 或编造批准。

1. 打开搜客清单。每一行有「可转线索」「未达门禁」或「已是线索」。未达门禁的一行写明缺什么。
2. 点开一条未达门禁的候选。详情里的「转为线索」列出缺项，没有确认按钮。
3. 点开一条已有当前账号人工可联系批准、且尚未转入的候选。详情写明将使用的已批准联系方式，并出现「转为线索」。
4. 点「转为线索」，在确认框里点取消。候选仍不是线索，也不会发开发信。
5. 再点「转为线索」并确认。成功后出现「查看线索」。点它可以打开这条线索；留在清单时，同一条变成已是线索，不能再转一次。
6. 若接口拒绝，提示里能看到服务端原文，候选不会被标成已转入。
7. 在智能获客里打开同一条候选的详情。资格说明与搜客清单一致。满足时也可以从这里确认转入。批量按钮同样只转入已满足门禁的候选，并在确认框里写明哪些不会转入。

## 11. 本地演示：可联系批准入口

用一条真实候选看缺项。不要为了走通去自动批准，也不要改 `convert_to_lead`。

1. 打开搜客清单。未达门禁、且缺项里写着「还缺当前业务员的人工可联系批准」的一行，旁边有「去申请可联系批准」。可转线索、已是线索没有这个按钮。只缺「尚未进入正式企业覆盖池」或其他缺项时，也只有文字，没有这个按钮。
2. 点这一行的「去申请可联系批准」。详情打开，并出现现有的「跟进前检查」。当前步骤是「允许跟进」。这一步没有提交批准，候选也没有变成线索。
3. 详情里同一个按钮再点一次，仍停在这份检查上，不会自己提交。
4. 若要真正批准，仍要点现有的「允许跟进」，并在确认框里确认。点取消后，候选仍是未达门禁，入口还在。确认后走原来的可联系批准接口。成功后这一行不再显示「去申请可联系批准」；变成可转线索之后，才能点「转为线索」。
5. 在智能获客里打开同一条尚未批准、且缺项是人工可联系批准的候选。详情里也有「去申请可联系批准」。候选已在搜客清单时，点它进入清单上的同一份检查；还没加入清单时，检查就开在当前详情里。两种情况都不会自动批准，也不会发开发信。

## 12. 本地演示：抑制、退订与退信原因

用一条真实候选看原因。不要编造原因，也不要加解除按钮。

1. 打开搜客清单。没有抑制、退订、退信或联系方式无效的候选，行上不出现原因条。
2. 有这类状态时，这一行能看到状态标签和原因。接口带回了来源时，同一行写出来源。没有原因时写「原因未回传」。
3. 点开同一条。详情里的标签、原因和来源与清单行一致，只读。
4. 这里没有解除抑制、恢复外发，或跳过转线索确认的按钮。要外发或转线索，仍走原来的确认和门禁。
5. 在智能获客里打开同一条候选的详情。原因说明与搜客清单一致。

## 13. 本地演示：已可联系后的跟进记录

用一条已经可联系、或已经有当前业务员人工可联系批准的真实候选。不要为了走通去改 `convert_to_lead`，也不要编造跟进。

1. 打开搜客清单。每一行能看到最近跟进：时间、类型和简短内容。还没有记录时，这一行写「暂无跟进」。
2. 点开一条已可联系、已联系，或已经是线索的候选。详情里的「跟进记录」与清单行一致。输入一句真实结论，点「记录跟进」。成功后最近跟进变成这一句，类型是备注。这一步不发送开发信，也不转为线索。
3. 什么都不写就点「记录跟进」，应停住，并说明要填写内容。候选资料不变。
4. 打开一条还没批准可联系、状态仍是待处理的候选。行上仍是「暂无跟进」或已有记录，但没有「记录跟进」按钮。不要为了写出这一条去自动批准。
5. 打开工作台。「最近触达」下面有一块「待记跟进」。没有已可联系的清单候选时，这里写明去搜客清单。不要出现编出来的公司名。
6. 有已可联系的清单候选时，每一行是公司名、状态，以及最近跟进或「暂无跟进」。最多 8 行。待处理、已排除、还没加入搜客清单的不出现。
7. 点一行。应进入搜客清单并打开这条候选的跟进输入框。页面说明不会发送，也不会转为线索。
8. 在智能获客里打开同一条已可联系、且已在搜客清单的候选。详情里的跟进与搜客清单一致，也可以从这里记一条。记完后清单行的最近跟进跟着变。
9. 已经是线索的候选，记下的这条也会出现在线索抽屉的跟进记录里。转线索的确认和 `approved_contactable` 门禁不变。

## 14. 本地演示：下次跟进

用一条已经可联系、或已经有当前业务员人工可联系批准的真实候选。不要为了走通去改 `convert_to_lead`，也不要编造跟进，也不要指望站外提醒。

1. 打开搜客清单。每一行能看到下次跟进。还没有设时间时，这一行写「未设下次跟进」。
2. 点开一条已可联系的候选。详情里的下次跟进与清单行一致。在「记录跟进」旁边可以选一个日期时间。只写跟进、不选时间，点「记录跟进」。最近跟进变成这一句，下次跟进仍是「未设下次跟进」。这一步不发送开发信，也不转为线索。
3. 再写一句跟进，并选一个还没到的时间，点「记录跟进」。清单行和详情都显示这个时间。什么都不写就点「记录跟进」，应停住，并说明要填写内容。时间不会被清掉。
4. 把时间改到一个已经过去的时刻，点「保存下次跟进」。可以不写新的跟进。清单行和详情标「已逾期」。今天之内还没到的时间标「今日到期」。
5. 清空时间再点「保存下次跟进」。回到「未设下次跟进」。不会多出一条跟进注记。
6. 打开一条还没批准可联系、状态仍是待处理的候选。行上仍是「未设下次跟进」或已有时间，但没有「保存下次跟进」。不要为了设时间去自动批准。
7. 打开工作台。「待记跟进」下面有一块「今日到期」。没有已逾期或今天要跟的候选时，这里写明去搜客清单设时间。不要出现编出来的公司名，也不会发到站外。
8. 有已逾期或今天到期的清单候选时，每一行是公司名、状态，以及「已逾期」或「今日到期」和时间。最多 8 行。待处理、已排除、还没加入搜客清单、下次跟进在今天之后的，都不出现。
9. 点一行。应进入搜客清单并打开这条候选的下次跟进时间。页面说明不会发送，也不会转为线索。
10. 已经是线索的候选，在这里改的下次跟进也会出现在线索的下次跟进上。转线索的确认和 `approved_contactable` 门禁不变。

## 15. 本地演示：获客阶段一眼可见

用搜客清单里已有的候选看阶段。不要为了走通去改 `convert_to_lead`，不要自动批准，也不要发送开发信。阶段是从现有字段推导出来的，没有另一套阶段表。开发信草稿不落库，所以没有单独的「草稿待发」；已可联系、有邮箱、还没发出的，标签写成「待写开发信」，筛选归在待触达。

1. 打开搜客清单。每一行最前面有当前阶段：待触达、待写开发信、已触达待批准、可联系、跟进中、已转线索、已抑制 / 已退订 / 已退信 / 联系方式无效，或已排除。原来的状态标签还在，不拿阶段替换它。
2. 还没发出开发信、也没有触达记录的，是待触达。清单状态已是可联系、邮箱已有、开发信还没发出的，是待写开发信。点开后说明里写明草稿不落库，发送前仍要确认。
3. 已经发出开发信或有触达记录，但当前账号还没有人工可联系批准的，是已触达待批准。发信时带上的下次跟进不把它算成跟进中。说明里写明不会自动批准。
